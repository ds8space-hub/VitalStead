## D-014. Форм-фактор MVP: Claude plugin + локальный MCP-сервер

MVP поставляется не как самостоятельное desktop-приложение, а как **Claude plugin**:
skill (доменные знания и правила настройки) + slash-команды + **локальный MCP-сервер**
(Rust-бинарь), который выполняет OAuth, синхронизацию и запись CSV.

Обоснование:

- ядро продукта (OAuth, sync, CSV) не зависит от UI — благодаря D-011 оно переносится
  без изменений;
- отпадают Tauri shell, React UI, deep-link, авто-апдейт, инсталлятор — самые дорогие
  части desktop-MVP;
- сценарий «ИИ помогает настроить и читает данные» становится первоклассным вместо
  Markdown-гайда.

Уточнение D-007: принцип «ИИ не встроен в продукт» сохраняется — продукт по-прежнему
не содержит ИИ; вместо генерации `AI_SETUP_GUIDE.md` знания мастера настройки
поставляются как skill внутри плагина. Пользователь сам выбирает и контролирует
свой ИИ-клиент.

Ограничение платформы: целевая среда MVP — **Claude Desktop** (macOS, затем Windows).
Web-версия claude.ai поддерживает только remote-коннекторы, что конфликтует с D-001,
поэтому web исключён осознанно (см. D-016). Голый MCP-сервер при этом остаётся
совместимым с любыми MCP-клиентами (Claude Code, Cursor и др.) — плагин лишь
Claude-специфичная упаковка.

Tauri desktop-приложение (родительский репозиторий) не отменяется — переносится в
post-validation трек для аудитории без MCP-клиента, поверх этого же ядра.

## D-015. Секреты и health-данные не попадают в контекст модели

Жёсткое правило границы доверия «модель ⇄ MCP-сервер»:

- все credentials (client secrets, access/refresh tokens, authorization codes) живут
  исключительно внутри MCP-сервера и OS-хранилища (Keychain / Credential Manager);
- tools никогда не принимают и не возвращают токены и секреты; OAuth-обмен целиком
  выполняется сервером (браузер + localhost callback), модель видит только статусы;
- health-данные попадают в ответы tools только по явному запросу пользователя;
  по умолчанию tools отдают агрегаты и метаданные (диапазоны дат, число записей),
  полный сырой архив существует только как CSV на диске;
- BYO credentials (D-006) вводятся через конфигурацию плагина/бандла с пометкой
  sensitive (хранение в Keychain), а не через чат.

Следствие для threat model: prompt injection в разговоре не должен позволять
эксфильтрацию секретов через tools — ни один tool не имеет доступа к секретам
в читаемом виде (см. EPIC-08).

## D-016. Каналы дистрибуции

- **Закрытый MVP** — personal marketplace (git-репозиторий с плагином), установка через
  вкладку Personal в Directory Claude. Без ревью Anthropic, обновления — pull из репозитория.
- **Публичный канал** — подача в директорию (Partners / desktop extensions) только
  post-MVP, после закрытого теста; требует privacy policy и прохождения ревью Anthropic.
- **Remote MCP-connector не делается ни на каком этапе**: health-данные через
  инфраструктуру Control Your Data не проходят (следствие D-001). Единственное
  серверное исключение в будущем — shared OAuth broker (родительский T-205), через
  который проходят только token-обмены, но не health-данные.

## D-017. Порядок провайдеров в EPIC-04: WHOOP первым, Oura — post-MVP

MVP реализует первым коннектор **WHOOP**, а не Oura, как было в исходном порядке
EPIC-04. Oura connector переносится в post-MVP трек.

Обоснование: продуктовое решение пользователя (владельца проекта) — приоритет
WHOOP как первого провайдера для валидации connector contract. Явных технических
причин для исходного порядка (Oura первым) в доках зафиксировано не было — это
был порядок по умолчанию, не жёсткая зависимость.

Следствия:

- `docs/tasks/EPIC-04-providers.md`: T-401 (WHOOP, теперь P0) реализуется первым;
  T-402 (Oura) переносится в post-MVP с сохранёнными критериями приёмки —
  переоткрывается как задача, когда придёт время;
- T-403 (connector contract доказан на двух провайдерах) в рамках MVP доказывается
  через WHOOP + чеклист расширяемости в `architecture.md` (реализация второго
  реального провайдера для контрактной проверки происходит только когда Oura
  вернётся в работу post-MVP — контракт для одного провайдера не может быть
  «доказан на двух» буквально, критерий скорректирован);
- `docs/roadmap.md`: M3 (OAuth end-to-end) описан провайдер-агностично (был
  сформулирован через Oura без технической необходимости); M4 (первый синк)
  теперь про WHOOP (T-401); M5 (Oura, второй провайдер) вынесен в post-MVP раздел
  вместе с остальными post-MVP треками.

Это уточняющее решение не отменяет и не противоречит D-001…D-016 — только меняет
порядок реализации провайдеров внутри уже существующего EPIC-04.

## D-018. EPIC-05 (Garmin: ручной ZIP-импорт) перенесён в post-MVP

MVP не включает Garmin-коннектор (ручной ZIP-импорт). Продуктовое решение

## D-019. Фиксированный OAuth callback port для дистрибуции (VITALSTEAD_OAUTH_FIXED_PORT=53682)

Проблема: `MacOSOAuthCallbackHandler::listen_for_callback` по умолчанию
привязывается к OS-назначенному порту (`127.0.0.1:0`), который меняется при
каждом запуске сервера. OAuth-провайдеры (WHOOP и любой будущий) требуют
точного совпадения `redirect_uri` с зарегистрированным в дашборде
BYO-приложения — динамический порт делает невозможной связку «один раз
зарегистрировал redirect URI → работает всегда» для пользователя, у которого
нет доступа к коду сервера, чтобы каждый раз проверять актуальный порт.

Решение: пакуемый плагин (T-703) и MCPB-бандл (T-704) фиксируют
`VITALSTEAD_OAUTH_FIXED_PORT=53682` в конфигурации запуска сервера (`.mcp.json` /
MCPB `manifest.json`), превращая уже существующий dev-only env var
(`platform/macos/oauth_callback_handler.rs`, введён на T-401 для ручного e2e)
в постоянный production-механизм. Skill (T-701) инструктирует пользователя
регистрировать redirect URI ровно `http://127.0.0.1:53682/callback` в
дашборде провайдера.

Обоснование: deep link / системный URL scheme выпали из scope ещё в
D-014/architecture.md «Кросс-платформенная граница» — loopback listener
выбран как кросс-платформенная замена. Раз выбран loopback listener, порт
должен быть предсказуем для пользователя; единственный способ сделать порт
предсказуемым без рефакторинга ядра OAuth state machine — зафиксировать его
на уровне конфигурации запуска, что уже поддерживается существующим env var
без изменений в `core/`.

Риск (не устраняется этим решением): если порт 53682 уже занят другим
процессом на машине пользователя, OAuth-подключение не сработает.
Задокументировано как известное ограничение в skill (T-701); fallback на
альтернативный порт — post-MVP доработка.

Следствия:

- `plugin/.mcp.json` (T-703) и `mcpb/manifest.json` (T-704) задают
  `VITALSTEAD_OAUTH_FIXED_PORT=53682` в окружении запуска сервера;
- `plugin/skills/setup-guide/SKILL.md` (T-701) инструктирует регистрировать
  именно этот redirect URI и объясняет риск занятого порта;
- роль `VITALSTEAD_OAUTH_FIXED_PORT` меняется с «dev-инструмент для ручного e2e» на
  «постоянный production-механизм»; сам код (`oauth_callback_handler.rs`,
  `examples/whoop_manual_connect.rs`) не меняется — только новое использование
  уже существующего env var.

Не отменяет и не противоречит D-001…D-018.

## D-020. Переименование MCP form-factor в Vitalstead

Продуктовое решение пользователя (владельца проекта): этот форм-фактор
(Claude plugin + локальный MCP-сервер, D-014) получает собственное имя
**Vitalstead** перед размещением в директории Anthropic. Анализ и проверка
коллизий — `docs/naming.md`.

Обоснование: «Control Your Data» остаётся именем родительского проекта
(`../Control your data`, Tauri desktop, post-validation трек) и общей идеи
владения своими данными; для листинга у Anthropic этому конкретному
plugin/MCP-продукту нужно собственное, проверяемое на коллизии, легко
произносимое английское имя (D-012). «Vitalstead» = vital + stead
(homestead/farmstead) — «усадьба для ваших витальных данных», без коллизий
в health/wearable/self-hosted нишах на момент проверки (2026-07-16).

Что переименовано (этот репозиторий, не родительский):

- `Cargo.toml`: package/lib/bin `control-your-data-mcp`/`control_your_data_mcp`
  → `vitalstead-mcp`/`vitalstead_mcp`;
- crate-путь `control_your_data_mcp::` в `src/main.rs`, `examples/` →
  `vitalstead_mcp::`; структура `CydMcpServer` → `VitalsteadMcpServer`;
- env-переменные `CYD_OAUTH_FIXED_PORT` → `VITALSTEAD_OAUTH_FIXED_PORT`,
  `CYD_DATA_FOLDER` → `VITALSTEAD_DATA_FOLDER` (уточняет конкретное имя
  переменной из D-019, сам механизм не меняется);
- Keychain service-префикс `cyd.<provider>.<connection_id>` →
  `vitalstead.<provider>.<connection_id>`;
- `plugin/.claude-plugin/plugin.json`, `plugin/.mcp.json`,
  `mcpb/manifest.json`, `.claude-plugin/marketplace.json`: имя плагина
  `control-your-data` → `vitalstead`, `display_name` → «Vitalstead»;
  `author`/`owner.name` остаётся «Control Your Data» (издатель/родительский
  бренд — плагин публикуется как «Vitalstead by Control Your Data»);
- README.md, CLAUDE.md, `docs/privacy.md`, `plugin/README.md`,
  `plugin/skills/setup-guide/SKILL.md`: упоминания продукта как «Control Your
  Data» заменены на «Vitalstead»; упоминания родительского репозитория
  (`../Control your data`) не тронуты — это другой, не переименовываемый
  проект.

Не переименовано намеренно:

- github remote `origin` (`github.com/veramey/CYD_MCP`, см.
  `docs/tasks/EPIC-07-plugin-packaging.md` T-703-примечание) — переименование
  реального GitHub-репозитория является отдельным, более consequential
  действием и не входит в это решение;
- собранные артефакты `plugin/bin/control-your-data-mcp`,
  `mcpb/server/control-your-data-mcp`, `mcpb/control-your-data.mcpb` —
  бинарные файлы под старым именем; актуализация требует пересборки
  (`cargo build --release`) и повторной упаковки (`mcpb pack`), см. задачу
  ниже.

Следствия:

- `docs/tasks/EPIC-07-plugin-packaging.md`: пути к бинарям/бандлу в тексте
  обновлены на `vitalstead-mcp`/`vitalstead.mcpb`; фактическая пересборка и
  замена закоммиченных бинарных артефактов — отдельный шаг (T-705 или новая
  задача EPIC-07), не выполнена этим изменением;
- `docs/tasks/EPIC-02/04/06-*.md`: упоминания `CYD_DATA_FOLDER`/
  `CYD_OAUTH_FIXED_PORT` обновлены на новые имена переменных;
- `cargo test` обязателен после переименования (Definition of Done) — крейт
  перекомпилируется под новым именем без изменения логики.

Не отменяет и не противоречит D-001…D-019.
