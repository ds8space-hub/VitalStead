# Threat model — MCP form factor

Дополняет родительскую threat model (`../Control your data/docs/mvp-plan/credentials-and-security.md`,
раздел «Минимальная threat model») — та часть (извлечение secret из приложения,
CSRF через `state`, подмена redirect URL, токены в crash report, formula
injection в CSV, path traversal, повреждение CSV при аварии, случайное
раскрытие секрета внешнему ИИ) действует здесь целиком и не переписывается.
Этот документ добавляет три сценария, специфичных для MCP-форм-фактора
(D-014) — новой границы доверия «модель ⇄ MCP-сервер» (D-015), которой не
было у родительского Tauri-приложения.

Для каждого сценария: конкретный вектор → почему mitigated (со ссылкой на
код/решение) или что не устранено и требует задачи.

## Сценарий A: prompt injection в разговоре → попытка эксфильтрации секретов/сырых данных через tools

### A1 — модель просят передать client_secret через tool-параметр

`connect_provider` принимает `client_id`/`client_secret` и как tool-параметры
(D-006, T-604), не только как env vars. Если инструкция (введённая
пользователем или injected через какой-то внешний контент) убедит модель
запросить у пользователя секрет в чат и передать его как параметр —
секрет физически может пройти через контекст модели, в обход
D-015 «жёсткого правила».

**Статус: смешанный.**
- Основной канал (plugin `userConfig` с `sensitive: true`, T-703; MCPB
  `user_config`, T-704) полностью обходит модель — секрет инжектится в env
  процесса сервера Claude Desktop/Code напрямую, tool-параметр не нужен.
- `skills/setup-guide/SKILL.md` (T-701) содержит явное «hard rule #1/#2»:
  никогда не запрашивать секрет в чат, вводить только через UI настроек
  плагина.
- **Устранено в этой сессии** (T-801): `ConnectProviderParams.client_id`/
  `client_secret` получили `#[schemars(description = "...")]` с явным
  предупреждением прямо в JSON-схеме параметров — эта строка видна модели
  в момент построения вызова tool, а не только в тексте skill, который
  модель может не перечитать посреди разговора. Схема — код-уровневый
  барьер, а не только процессный (см. `src/main.rs`).
- Остаточный риск: параметр как таковой не удалён (D-006 явно требует
  поддержку BYO без плагина — например, прямой запуск бинаря с ручной
  конфигурацией), значит полностью технически исключить путь «секрет как
  строка в tool call» нельзя без нарушения D-006. Принято как осознанный
  trade-off, а не незакрытая дыра.

### A2 — модель просят вызвать `query_data(include_raw: true)` и без спроса выдать значения наружу

**Статус: mitigated процессом, частично — кодом.**
- Код: `include_raw` по умолчанию `false` (D-015), tool description
  (`src/main.rs`, `query_data`) прямо говорит, что raw-значения попадут в
  контекст разговора — это не скрытое поведение.
- Skill (T-701, шаг 9) прямо инструктирует модель: если пользователь просит
  raw-данные, сказать об этом явно, не молча выполнять.
- Остаточный риск: если raw-данные уже вошли в контекст (по легитимному
  запросу пользователя), их дальнейшее использование моделью (куда их
  вставить/переслать) — общий LLM-safety вопрос, не специфичный для этого
  проекта и не решаемый на уровне MCP-сервера (сервер не знает, что модель
  делает с уже полученным ответом). Не задача этого проекта устранять этот
  класс риска целиком — только не увеличивать его (что и обеспечивает
  D-015: raw — опция, не поведение по умолчанию).

### A3 — модель просят вызвать `delete_app_data` или `disconnect_provider` разрушительно

**Статус: mitigated.**
- `disconnect_provider` никогда не удаляет CSV (D-010, проверено тестами
  T-605) — максимальный ущерб от необдуманного вызова — необходимость
  переподключения, не потеря данных.
- `delete_app_data` — явный отдельный вызов (T-606), не триггерится никаким
  другим flow автоматически; ответ различает success/partial/error, не
  маскирует частичный сбой.
- Skill (T-701, шаг 10) прямо указывает: `delete_app_data` — «separate,
  explicit action — never triggered automatically»; модель должна получить
  это как контекст перед тем, как предлагать это пользователю.
- Общее поведение агента (подтверждать разрушительные действия с
  пользователем) — вне границ MCP-сервера, регулируется на уровне
  CLAUDE.md/системного промпта хоста, не этим проектом.

## Сценарий B: вредоносный контент в ответах провайдера → отражение в tool-ответ

**Статус: mitigated структурой данных, для текущего провайдера.**
- Проверены все поля WHOOP DTO (`src/core/connectors/whoop/dto.rs`): `id`,
  `external_id`, `sleep_id`, `cycle_id` — провайдер-генерируемые
  идентификаторы; `score_state` — фиксированный enum-подобный набор
  значений; остальные поля — числа/timestamps/`timezone_offset`. **Свободных
  текстовых полей, которые WHOOP мог бы заполнить произвольным
  attacker-контролируемым текстом, в текущей схеме нет** — inject-поверхность
  для prompt injection через тело ответа провайдера у WHOOP отсутствует
  по факту, не только по намерению.
- CSV formula injection (родительский пункт, не переоткрывается, но здесь
  уточняется статус): `core/csv/serialize.rs` **не экранирует** ячейки,
  начинающиеся с `=`, `+`, `-`, `@` — если такое значение попадёт в CSV и
  пользователь откроет файл в Excel/Google Sheets, возможна интерпретация
  как формулы. Для WHOOP это не эксплуатируемо сегодня (см. выше — нет
  attacker-контролируемых текстовых полей), но `core/csv` — provider-агностичный
  модуль, который будущие провайдеры (Oura, post-MVP D-017) будут
  переиспользовать без изменений, и не все провайдеры гарантированно будут
  иметь такую же «чистую» схему. **Не устранено — заведена задача.**
  См. `docs/tasks/EPIC-08-security.md` T-804 (новая, ниже).
- Malformed/неожиданный JSON от провайдера: `WhoopApiError::MalformedResponse`
  никогда не включает тело ответа (проверено тестом
  `test_fetch_page_malformed_json_does_not_leak_body_in_error`, `client.rs`);
  диагностика через `redact_json_shape()` — структура ключей логируется,
  значения всегда `<REDACTED>` независимо от типа (проверено чтением кода).

## Сценарий C: локальный процесс на 127.0.0.1 во время OAuth — перехват/спуфинг callback

Родительский документ уже требует рассмотреть «перехват OAuth callback» и
«CSRF через неверный state» в общем виде; здесь — конкретно про loopback
listener этого проекта (T-301/302, `platform/macos/oauth_callback_handler.rs`,
`core/oauth/authorization.rs`).

### C1 — другой процесс на машине пользователя занимает порт раньше нас

**Статус: безопасный отказ, не тихий hijack.**
`AuthorizationFlow::start_and_bind` (T-604) сначала биндит listener и только
потом строит authorization URL с реальным полученным портом и открывает
браузер (порядок операций был исправлен именно в T-604 — раньше URL
строился до бинда, что было реальным багом). Если порт 53682 (D-019) уже
занят другим процессом, `TcpListener::bind` вернёт ОС-ошибку немедленно —
сервер не сможет забиндиться и не откроет браузер на потенциально чужой
listener; пользователь получает ошибку подключения, а не тихую подмену.
Задокументировано как известное ограничение в skill (T-701: «close whatever
might be using that port and retry»).

### C2 — сторонний процесс/сайт пытается подделать callback (угадать/подсмотреть state)

**Статус: mitigated.**
- `state` — `Uuid::new_v4()` (`AuthorizationFlow::generate_state`,
  122 бита случайности) — неугадываем перебором в разумное время.
- Pending-authorization store принимает только ОДНО совпадение
  `(connection_id, provider, state)`, повторное/просроченное предъявление
  отклоняется (T-302) — replay после первого валидного callback не проходит.
- Listener биндится на `127.0.0.1`, не `0.0.0.0` — недостижим по сети с
  других машин, только с локального хоста.
- Таймаут ожидания — 5 минут (T-006 L104-106), после которого pending
  authorization истекает.
- Остаточный риск: локальный процесс с УЖЕ имеющимся кодовым исполнением на
  машине пользователя (тот же уровень привилегий, что у самого Claude
  Desktop) теоретически мог бы прочитать `state` из аргументов процесса
  браузера/истории. Это требует, чтобы машина пользователя уже была
  скомпрометирована на уровне, дающем такой доступ — за пределами модели
  угроз OAuth-флоу как такового (тот же trust boundary, который родительский
  документ неявно принимает для Keychain: если атакующий уже выполняет код
  с правами пользователя, Keychain и локальные файлы тоже под угрозой,
  независимо от этого проекта).

## Ревью tool descriptions — ни один tool не побуждает модель передавать секреты

Проверены все 8 tool descriptions (`src/main.rs`, `#[tool(description = ...)]`):
`list_data`, `connect_provider`, `disconnect_provider`, `set_data_folder`,
`delete_app_data`, `sync_provider`, `sync_now`, `query_data`. Ни одно
описание не инструктирует модель запросить у пользователя пароль, secret,
токен или authorization code — единственные два поля, которые формально
МОГУТ нести секрет (`connect_provider.client_id`/`client_secret`), теперь
несут явное предупреждение в самой JSON-схеме (см. Сценарий A1 выше).
