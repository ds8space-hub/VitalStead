## T-702 [P1] Slash-команды ✅ (частично — /import-garmin отложена)

Критерии приёмки:

- `/connect <provider>`, `/sync`, `/import-garmin <path>`, `/disconnect <provider>`;
- каждая команда — тонкая обёртка над соответствующим tool с проверкой аргументов;
- сообщения об ошибках используют каталог ошибок T-203 (единые recovery-подсказки).

Выполнено 2026-07-16: `plugin/commands/{connect,sync,disconnect}.md`. Каждая —
тонкая обёртка: парсит `$ARGUMENTS`, вызывает соответствующий tool
(`connect_provider`/`sync_now`/`sync_provider`/`disconnect_provider`), инструктирует
модель ретранслировать `error.message`/`error.recovery` из ответа tool дословно,
а не изобретать собственные объяснения (единый каталог ошибок T-203,
`error_mapping.rs`). `/connect` делегирует в `setup-guide` skill (T-701) вместо
прямого вызова tool — там уже есть точные шаги (redirect URI, scopes) и
D-015-совместимая обработка ошибок.

`/import-garmin <path>` НЕ создана: соответствующий tool `import_garmin_zip`
не существует — Garmin/EPIC-05 отложен в post-MVP решением D-018, принятым
раньше в этой же сессии. Команда будет добавлена вместе с реализацией
EPIC-05, когда придёт время (не блокирует остальной EPIC-07 — Garmin и так
не входит в закрытый MVP).

## T-703 [P0] Манифест плагина + personal marketplace ⚠️ частично (см. ниже)

Канал закрытого MVP (D-016).

Критерии приёмки:

- `.claude-plugin/plugin.json` собирает skill (T-701), команды (T-702) и конфигурацию
  запуска локального MCP-бинаря;
- отдельный git-репозиторий marketplace; установка проверена на чистой машине через
  Directory → Plugins → Personal → Add marketplace;
- README onboarding для тестеров: предустановки (бинарь/платформа), установка,
  первое подключение, как сообщать о проблемах;
- обновление плагина у тестера доставляется pull'ом marketplace — проверено.

Выполнено 2026-07-16 (в пределах возможностей агента):

- `plugin/.claude-plugin/plugin.json` — манифест + `userConfig` для
  `whoop_client_id`/`whoop_client_secret` (последний `sensitive: true` —
  подтверждено через research: Claude Code хранит такие значения в Keychain/
  `~/.claude/.credentials.json` и инжектит их в env запускаемого MCP-сервера
  через `${user_config.*}` подстановку в `.mcp.json`, **никогда не проходя
  через контекст модели** — это и есть механизм для D-006/D-015 в plugin-канале,
  не только в MCPB, как ошибочно предполагалось изначально).
- `plugin/.mcp.json` — запускает `${CLAUDE_PLUGIN_ROOT}/bin/vitalstead-mcp`
  (stdio), передаёт `VITALSTEAD_OAUTH_FIXED_PORT=53682` (D-019, принято в этой же
  сессии) и `WHOOP_CLIENT_ID`/`WHOOP_CLIENT_SECRET` из `userConfig`.
- `plugin/bin/vitalstead-mcp` — реальный `cargo build --release`
  бинарь (arm64, Mach-O, `aarch64-apple-darwin` — архитектура машины
  разработки), **лично прогнан smoke-test**: отвечает на MCP `initialize` и
  `tools/list` по stdio, отдаёт все 8 tools (`connect_provider`,
  `disconnect_provider`, `delete_app_data`, `list_data`, `query_data`,
  `set_data_folder`, `sync_now`, `sync_provider`) — не просто скомпилирован,
  реально протестирован как MCP-сервер.
- `plugin/README.md` — onboarding: prerequisites (macOS arm64 сейчас,
  x86_64 — сборка из исходников до T-704), установка через
  Directory → Plugins → Personal → Add marketplace, первое подключение
  (делегирует в setup-guide skill), как сообщать о проблемах (что можно/нельзя
  присылать, D-015), обновление через pull marketplace.
- `.claude-plugin/marketplace.json` (в корне ЭТОГО репозитория, не отдельного)
  — `plugins: [{name: "vitalstead", source: "./plugin"}]`. Решение:
  использовать существующий репозиторий (`origin` уже настроен на
  `github.com/veramey/CYD_MCP`) как marketplace-репозиторий вместо создания
  нового пустого, чтобы не плодить внешнюю инфраструктуру без необходимости —
  прагматичный выбор для MVP, задокументирован явно, НЕ равнозначен буквальному
  требованию критерия «отдельный git-репозиторий» (тестеры при таком выборе
  видят весь исходный код ядра, а не только упакованный плагин).

НЕ выполнено — вне возможностей агента, требует действий пользователя:
- Буквально «отдельный» (source-only, без истории ядра) marketplace-репозиторий,
  если это желаемо взамен текущего прагматичного выбора — механическое
  копирование `plugin/` + `.claude-plugin/marketplace.json` в новый репозиторий,
  решение и создание репозитория — за пользователем.
- «Установка проверена на чистой машине через Directory → Plugins → Personal →
  Add marketplace» — интерактивное действие в GUI Claude Desktop на отдельной
  машине; агент может подготовить и провалидировать файлы, но не может
  физически провести этот UI-флоу. Требуется ручная проверка пользователем
  (или тестером) перед тем, как считать критерий полностью закрытым.
- «Обновление у тестера доставляется pull'ом marketplace — проверено» —
  та же причина: требует реального повторного цикла install→update на
  стороне тестера.

## T-704 [P1] MCPB-бандл для Claude Desktop ⚠️ частично (см. ниже)

One-click канал (D-016, M7 — исправлена устаревшая ссылка на M8, см. roadmap.md).

Критерии приёмки:

- `manifest.json` с `user_config`: `data_folder` (тип directory),
  `client_id`/`client_secret` для BYO (`sensitive: true` → OS Keychain);
- server.type = binary, собранный Rust-бинарь для macOS (arm64 + x86_64);
- установка `.mcpb` на чистой macOS проверена; зафиксировано, требует ли Gatekeeper
  подписи/нотризации бинаря, и если да — процесс подписи описан в этом файле;
- секреты из user_config не появляются в конфиг-файлах и логах (проверено).

Выполнено 2026-07-16 (в пределах возможностей агента):

- `mcpb/manifest.json` — реальная официальная схема MCPB (не угадана):
  установлен `@anthropic-ai/mcpb` CLI, манифест прогнан через `mcpb validate` —
  проходит. `manifest_version: "0.3"`, `server.type: "binary"`, `user_config`
  с `data_folder` (`type: "directory"`), `whoop_client_id`/`whoop_client_secret`
  (последний `sensitive: true`) — та же ${user_config.*}-подстановка в
  `mcp_config.env`, что и в plugin-канале (T-703), секреты никогда не проходят
  через контекст модели.
- **arm64 + x86_64 — оба собраны и объединены в один universal-бинарь** через
  `lipo -create` (`rustup target add x86_64-apple-darwin` +
  `cargo build --release --target x86_64-apple-darwin`, кросс-компиляция с
  Apple Silicon без Rosetta) — `mcpb/server/vitalstead-mcp`,
  подтверждено `lipo -info`: `x86_64 arm64`. Один `command` путь в манифесте
  работает на обеих архитектурах Mac без `platform_overrides` — сознательный
  выбор вместо архитектурно-специфичных путей (схема `platform_overrides` в
  документации МCPB была неоднозначна по ключам darwin/darwin-x64/arch,
  universal-бинарь снимает эту неоднозначность полностью).
- Universal-бинарь лично прогнан smoke-тестом (initialize + tools/list по
  stdio, 8 tools, arm64-часть исполнена нативно на машине разработки).
- `.mcpb` упакован и провалидирован: `mcpb pack . vitalstead.mcpb` →
  `mcpb info` подтверждает валидный архив (6.6MB packed / 16.2MB unpacked).

НЕ выполнено — вне возможностей агента, требует действий/решений пользователя:

- **Подпись/нотаризация бинаря для Gatekeeper.** Официальная документация
  MCPB НЕ фиксирует явно, требует ли Claude Desktop подписанный бинарь внутри
  `.mcpb` (research: "MCPB spec focuses on bundle format, not downstream macOS
  binary requirements... I cannot confirm this from official docs"). `.mcpb`
  сейчас **не подписан** (`mcpb info` печатает `WARNING: Not signed`).
  Стандартный путь для публичной дистрибуции — `codesign` + `xcrun notarytool`
  (обычные Apple-инструменты, не специфичные для MCPB) с Developer ID
  Certificate, что требует платного Apple Developer Program membership —
  решение и оплата за пользователем. `mcpb sign --self-signed` доступен для
  внутреннего/dev-распространения без похода к Apple, но не снимает
  Gatekeeper-предупреждение при первом запуске на чужой машине (стандартный
  macOS UX для неподписанных приложений — обход через правый клик → Open).
- **Проверка на реальной чистой macOS.** Как и в T-703 — агент может собрать
  и провалидировать артефакт, но не может физически провести дабл-клик
  `.mcpb` → импорт в Claude Desktop → согласие на `user_config` на отдельной
  машине. Критерий требует ручной проверки пользователем/тестером.

## T-705 [P2] Подача в публичную директорию (post-MVP) ⛔ не подана

Критерии приёмки:

- privacy policy: что хранится локально, что уходит провайдерам, что попадает
  в контекст модели (по материалам T-803);
- контакт поддержки, тестовые credentials для ревью Anthropic;
- заявка подана по актуальному процессу (форма для desktop extensions);
- фидбек ревью превращён в задачи.

Выполнено 2026-07-16 (частично, заранее относительно T-803 — EPIC-08 ещё не
начат): `docs/privacy.md` — privacy policy на английском (D-012), написана по
фактическому поведению tools (не по намерениям): что в CSV/config/Keychain,
что уходит в WHOOP API, что попадает в контекст модели по умолчанию
(агрегаты, T-603) vs по явному `include_raw: true`, что не собирается вовсе
(D-013/D-005). Когда EPIC-08/T-803 стартует, этот документ становится его
основой/дублируется туда, а не переписывается с нуля.

НЕ выполнено — сознательно, вне полномочий агента:

- **Заявка не подана.** Подача требует реального контакта поддержки
  (email/организация пользователя) и тестовых credentials для ревьюеров
  Anthropic (реальный WHOOP developer app пользователя) — агент не должен
  действовать от имени пользователя перед третьей стороной (Anthropic) без
  его прямого участия, и не может подставить свои/фиктивные данные вместо
  реальных контактов пользователя (это было бы отправкой заявки не от
  реального владельца проекта). Задача остаётся открытой до тех пор, пока
  пользователь сам не решит: (1) когда подавать (P2/post-MVP — не блокирует
  ничего в MVP), (2) какой контакт поддержки указывать, (3) какие credentials
  предоставить ревьюерам.
- «Фидбек ревью → задачи» — зависит от (не начатой) подачи, соответственно
  тоже открыто.
