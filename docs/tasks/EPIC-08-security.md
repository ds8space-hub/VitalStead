## T-804 [P2] CSV formula injection guard (найдено при T-801, не блокирует MVP) ✅

Критерии приёмки:

- `core/csv/serialize.rs` экранирует ячейки, начинающиеся с `=`, `+`, `-`, `@`
  (OWASP CSV injection guidance) при записи, не нарушая byte-for-byte
  round-trip инвариант с `parse.rs` (`test_parse_roundtrip_matches_serialize`)
  и upsert-стабильность по `external_id` (T-007);
- покрыто тестом: значение вида `=cmd|...` записывается в безопасной форме,
  читается обратно без потери исходного значения для upsert-сравнения.

Не блокирует MVP — WHOOP DTO (`core/connectors/whoop/dto.rs`) не содержит
свободных текстовых полей, эксплуатировать сегодня нечем. Должно быть
закрыто до подключения любого провайдера со свободными текстовыми полями
(например Oura, если у неё есть поля вроде заметок/названий — проверить при
реализации T-402).

Выполнено 2026-07-17: `escape_formula_injection()` (`core/csv/serialize.rs`)
— если значение начинается с `=`/`+`/`-`/`@`, перед RFC4180-экранированием
добавляется ведущий `'` (стандартный OWASP-приём: spreadsheet-приложения
трактуют его как маркер «это текст», формулу не исполняют). Симметричная
`unescape_formula_injection()` (`core/csv/parse.rs`) снимает этот маркер при
чтении — round-trip для собственных нужд программы (сравнение upsert,
повторная сериализация) остаётся lossless, защита на диске сохраняется.
Порядок операций проверен: guard применяется ДО RFC4180-квотирования на
записи и ПОСЛЕ RFC4180-разэкранирования на чтении — так что запятая/кавычка,
случайно образовавшиеся из-за добавленного `'`, всё равно корректно
квотируются.

Upsert-стабильность (T-007) не нарушена структурно: `apply_new_row`
(`core/csv/upsert.rs`) сравнивает записи по `updated_at`, а не по
побайтовому равенству ячеек — guard/unguard не может вызвать ложное
"обновление" или "пропуск".

Существующий `test_parse_roundtrip_matches_serialize` не тронут и проходит
без изменений (его фикстуры не начинаются с `=+-@`, guard не срабатывает).
Добавлено 4 новых теста: guard действительно добавляет `'` перед всеми 4
триггер-символами и не трогает обычные значения (включая `-`/`@` В СЕРЕДИНЕ
строки — `2026-07-10`, `user@example.com`); отдельный round-trip тест
доказывает, что `=cmd|...` записывается с guard'ом на диске, но читается
обратно как исходное `=cmd|...`, без утери для upsert-сравнения — именно то,
что требовал критерий приёмки.

Задокументированное ограничение (принято, не блокирует): значение, которое
ГЕНУИННО начинается с `'=`/`'+`/`'-`/`'@` буквально (не от нашего guard'а),
неотличимо от экранированного и потеряет ведущую кавычку при чтении —
стандартный, широко принятый trade-off этого класса mitigation (не решается
без второго зарезервированного символа); не актуально для текущих данных
WHOOP, задокументировано в коде для будущего провайдера с текстовыми полями.

`cargo test`: 218 lib (+4 к T-802/803, было 214) + 49 bin, `cargo clippy
--all-targets`: чисто (1 новый warning `redundant_guards` найден и исправлен
в процессе).

## T-802 [P0] Аудит логирования ✅

Критерии приёмки:

- по всему коду сервера проверено правило: никогда не логируются Authorization
  headers, access/refresh tokens, client secrets, authorization codes, полные
  callback URL, полные API-ответы с health-данными;
- секреты в памяти проходят только через `SecretString` (Debug/Display не раскрывают
  значение) — проверено тестом на каждый новый тип с секретом;
- тест или lint-проверка ловит появление `format!`/лога с `SecretString` внутри.

Выполнено 2026-07-16: ручной аудит всех вызовов логирования
(`tracing::info!/warn!/error!/debug!`) по всему `src/` — грепом по всем
`expose_secret()` call sites (единственный способ достать сырое значение из
`SecretString`, т.к. Debug редактирован, а Display не реализован вовсе —
`format!("{}", secret)` не компилируется) и всем логам, упоминающим
token/secret/password/authorization/code. Все call sites — легитимные
(HTTP-запросы к провайдеру, запись в Keychain, тестовые assertions), ни
одного в логе. Один пограничный случай разобран явно: `connect.rs:229`
логирует полный authorization URL (`tracing::info!(url = %authorization_url)`)
— это НЕ нарушение правила «не логировать callback URL»: это исходящий URL
на страницу провайдера (client_id/redirect_uri/state/scope), а не входящий
callback с `code`; в URL нет ни code, ни client_secret, ни токена. Решение
задокументировано в самом коде ещё на T-401.

Новое: `src/core/security/log_lint.rs` (`#[cfg(test)]`) — автоматический
regression guard, не полагающийся только на ручной аудит. Статически
сканирует каждый `.rs` файл под `src/`, находит вызовы log-макросов
(`tracing::{info,warn,error,debug,trace}!`, а также unqualified-формы,
`println!`/`eprintln!`) со сбалансированным подсчётом скобок (не naive regex
по строке — макрос может занимать несколько строк) и проверяет, входит ли
`expose_secret()` в список аргументов. 4 self-теста доказывают, что сканер
реально ловит паттерн (не просто «ничего не находит, потому что сломан») —
включая честно задокументированное ограничение (ложные срабатывания на
текст внутри doc-комментариев допустимы для security-линта, ложноотрицательные
результаты — нет). `cargo test`: 214 lib (+5 к T-603, было 209) + 49 bin,
`cargo clippy --all-targets`: чисто.
