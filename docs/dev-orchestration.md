# Оркестрация реализации агентами (3 роли)

Адаптация `T-012-DEV-ORCHESTRATION.md` родительского проекта под этот репозиторий.
Паттерн тот же (contract-driven, quote-then-code, diff-review); отличия: нет
frontend-роли (UI-слоя в проекте нет), карта контрактов указывает на доки этого
репозитория, security-чек-лист расширен границей «модель ⇄ tools» (D-015).

## Три роли

### 1. Оркестратор — `solution-architect`, model: **Sonnet**

- Читает контракт **до** начала работы; новых контрактных файлов не создаёт.
  Карта контрактов этого репозитория:
  - `docs/decisions.md` → границы scope (D-014…D-016 + унаследованные D-001…D-013);
  - `docs/architecture.md` → компоненты, граница доверия, OAuth loopback,
    атомарность синка, платформенная граница;
  - `docs/tasks/EPIC-0X-*.md` → цель и критерии приёмки конкретной T-задачи;
  - родительские доки как источник унаследованных контрактов:
    `credentials-and-security.md` (OAuth/Keychain/логи), `providers.md`
    (rate limits, scopes), `csv-contract.md` + `T-007-SCHEMA-UPSERT.md` (CSV);
- разбивает T-задачу на шаги для Разработчика (spec, не код);
- после реализации делает diff-review: пункт контракта → реализация →
  совпадает/нет; субъективных оценок нет.

### 2. Разработчик — `backend-developer`, model: **Haiku**

- Rust-core: MCP tools, connectors, sync engine, OAuth, CSV, адаптеры;
- **quote-then-code**: перед реализацией — таблица трассируемости
  (пункт контракта файл:раздел → что реализуется); код без привязки не пишется;
- запрещённые формулировки: «заодно добавлю», «предполагаю, что», «на основе
  распространённой практики». Гап в контракте → эскалация Оркестратору,
  не додумывание;
- пишет unit-тесты вместе с кодом; `cargo test` зелёный — часть сдачи.

### 3. Тестировщик — `qa-engineer`, model: **Sonnet**

- прогоняет Gate 1 (все тесты, компиляция без warnings в новом коде);
- **встроенная security-проверка** в каждом прогоне: чек-лист из CLAUDE.md →
  Security rules (логи без секретов, `SecretString`, callback URL), плюс
  D-015-проверки: tool-ответы без токенов/сырых health-данных по умолчанию,
  state-валидация callback, path traversal на путях из tool-аргументов,
  CSV injection;
- расхождение → задача Разработчику со ссылкой на пункт контракта
  («не совпадает с X:раздел Y», не «показалось подозрительным»).

## Порядок работы

```
Оркестратор (контракт → шаги)
   → Разработчик (quote-then-code + unit-тесты)
      → Тестировщик (Gate 1 + security-чек-лист)
         → при провале: назад к Оркестратору
         → максимум 3 цикла на одну T-задачу
         → 4-й провал подряд: остановка и эскалация пользователю, не ретраи
```

## Когда запускается

С первой кодовой задачи этого репозитория — **T-201** (EPIC-02) — и далее для
каждой T-задачи. Документационные задачи (уточнения decisions/architecture)
трёхролевой цикл не требуют.

Роли вызываются прямыми `Agent`-вызовами (не `/team-implement` — 5–18-ролевая
команда избыточна для соло-проекта). Масштабирование (например, параллельная
разработка двух коннекторов в EPIC-04) — отдельное решение, здесь заранее
не предусмотрено.
